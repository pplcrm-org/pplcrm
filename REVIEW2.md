# Second production-risk review — the areas the first review did not read

Read-only review. No code was changed by it.

`REVIEW.md` at the repo root is the first production-risk review of this codebase. It covered the background job workers, the Stripe money paths, newsletter sending, list membership, configuration and boot, the tRPC authentication middleware, and the public REST surface. All fifteen of its findings have been fixed. Its own "Coverage gaps" section lists what it never opened, ranked by risk: the authentication controller, the database schema baseline, the mailbox sync services, blob storage and signed downloads, the Cloudflare Workers, the entire Angular frontend, both volunteer companion apps, the marketing website, and roughly twenty backend modules.

This review reads those areas. Nothing the first review already found is re-reported. Two items carried over from the first review are confirmed fixed and are not repeated: the NUL byte in `apps/backend/src/trpc.ts` is gone, and Stripe subscription events now have an ordering guard.

Every finding below was read in the source, and every file and line reference in this document was opened and confirmed.

One correction to a premise carried in from earlier notes: the `go.pplcrm.com` worker is **not** a short-link redirector. It serves the volunteer companion application and proxies the public REST paths to the backend. There is no destination-URL parameter in either worker, so the open-redirect and server-side-request-forgery class does not apply to them.

### 1. [HIGH] A queued export of "users" writes every colleague's password hash and two-factor code into a CSV file in blob storage

- **Where:** [export.handlers.ts:76-80](apps/backend/src/app/lib/jobs/handlers/export.handlers.ts#L76-L80) and [:118-124](apps/backend/src/app/lib/jobs/handlers/export.handlers.ts#L118-L124), with the entity mapping at [export-tables.ts:19-33](apps/backend/src/app/modules/exports/export-tables.ts#L19-L33), the column behaviour at [csv-stream.ts:23-31](apps/backend/src/app/lib/csv-stream.ts#L23-L31), and the input schema at [core.schema.ts:172-177](libs/common/src/lib/schemas/core.schema.ts#L172-L177).
- **Trigger:** One API call — queue an export of the `users` entity. Any signed-in member who can write is allowed to make it; `exports.queue` is a plain authenticated procedure.
- **What breaks:** The SQL is `selectFrom(table).selectAll()` and `table` is `authusers` for the `users` entity, so every column of the row is fetched regardless of what was asked for. Two variants follow from that:
  - **The requested `columns` list is itself never validated.** [core.schema.ts:175](libs/common/src/lib/schemas/core.schema.ts#L175) declares it as `z.array(z.string()).optional()` with no allow-list, and [csv-stream.ts:31](apps/backend/src/app/lib/csv-stream.ts#L31) emits exactly the named keys out of the fetched row. A caller who sends `columns: ['email','password','two_factor_code']` gets precisely those three columns. This is a directly targetable request, not an omission bug.
  - **Omitting `columns` is the lazy version of the same attack.** With no list, the CSV writer takes its header from the keys of the first row ([csv-stream.ts:23-27](apps/backend/src/app/lib/csv-stream.ts#L23-L27)) and emits every column.
    `authusers` holds `password`, `password_reset_code`, `two_factor_code`, `previous_email` and `previous_role` ([schema.sql:115-141](apps/backend/src/app/_migrations/schema.sql#L115-L141)). The password is an argon2 hash and the reset code is the hash of a 32-byte random token, so neither is directly usable. The two-factor code is a six-digit number hashed with unsalted SHA-256 ([controller.ts:1439-1445](apps/backend/src/app/modules/auth/controller.ts#L1439-L1445), [token-hash.ts:7-9](apps/backend/src/app/lib/token-hash.ts#L7-L9)), and one million candidates is a trivial search.
- **How far the two-factor code gets you, precisely:** less far than it first appears. The code expires after five minutes ([controller.ts:1445](apps/backend/src/app/modules/auth/controller.ts#L1445)), is set to null on a successful verification ([controller.ts:2077-2085](apps/backend/src/app/modules/auth/controller.ts#L2077-L2085)) and is cleared after five wrong guesses ([controller.ts:2044-2052](apps/backend/src/app/modules/auth/controller.ts#L2044-L2052)). A cracked hash therefore only yields a live code against an account that has an unfinished sign-in challenge at that exact moment, and the attacker still needs that account's password. It is a real weakening of the second factor, not a standalone route to another account.
- **Campaign scoping is also bypassed.** The export job runs on a raw Kysely handle inside the background worker with no campaign pin, whereas an ordinary read is campaign-scoped by `runWithTenant(..., pinnedCampaign)` at [trpc.ts:284](apps/backend/src/trpc.ts#L284). A campaign-restricted user who queues an export receives the whole tenant's rows for that table.
- **What on-call sees:** Nothing. It is an ordinary successful export.
- **Blast radius:** Every account in one workspace. Combined with finding 10 (exports are downloadable by any member and are never deleted), the file stays available indefinitely.
- **Confidence:** High. Every file in the chain read directly.
- **Fix sketch:** Give each export entity an explicit column allow-list and apply it to the SQL `select`, not only to the CSV header — gating the header alone leaves the explicitly-named-column variant working, because `selectAll()` still fetches the credential columns into memory. Never let an absent `columns` mean "all columns" on a table that holds credentials.

### 2. [HIGH] A canvassing volunteer's offline queue stops forever after one lost network response

- **Where:** the phone at [canvass-store.ts:703-719](apps/companion/src/app/canvass/canvass-store.ts#L703-L719), [:845-856](apps/companion/src/app/canvass/canvass-store.ts#L845-L856) and [:624-631](apps/companion/src/app/canvass/canvass-store.ts#L624-L631); the server at [canvassing/controller.ts:1252-1258](apps/backend/src/app/modules/canvassing/controller.ts#L1252-L1258).
- **Trigger:** A volunteer adds a new person at a door and records a survey for them. The batch reaches the server and is applied, but the response is lost — a dropped mobile connection, which is the exact situation this offline app exists for. The phone re-sends.
- **What breaks:** The phone creates the person with a temporary id and depends on the server's acknowledgement to hand back the real one. On the re-send, the idempotency ledger sees the operation id already recorded and returns `{ status: 'duplicate' }` with no `person_id` — the real id was never stored, so it cannot be returned. The phone removes the operation from its queue anyway ([:707](apps/companion/src/app/canvass/canvass-store.ts#L707)) but performs the id swap only when a person id is present ([:714](apps/companion/src/app/canvass/canvass-store.ts#L714)). The queued survey now points at a temporary id nothing will ever resolve. `sendableBatch` stops at the first unresolved temporary id ([:850](apps/companion/src/app/canvass/canvass-store.ts#L850)), returns an empty batch, and the flush sets the status to `error` and gives up ([:628-631](apps/companion/src/app/canvass/canvass-store.ts#L628-L631)). Every later flush does the same. The queue never drains again — not just that survey, but everything recorded after it, at every door.
- **What the volunteer sees:** A small sync-issue badge. The walk list still shows the doors as recorded, because the local overlay is intact. The work stays undelivered until they tap "End shift on this device", which deletes it.
- **Blast radius:** One volunteer's shift from the stuck operation onward. Surveys carry do-not-contact requests and subscription opt-ins, so this is a consent failure as well as lost data.
- **Confidence:** High. All four locations read directly; the acknowledgement type ([canvassing.schema.ts:280-286](libs/common/src/lib/schemas/canvassing.schema.ts#L280-L286)) confirms `person_id` is only ever sent on first application.
- **Fix sketch:** Store the created person's id on the ledger row when the operation is first applied — `companion_ops` currently has only tenant, operation id, scope and timestamp ([schema.sql:458-464](apps/backend/src/app/_migrations/schema.sql#L458-L464)), so this needs a small migration — and return it on the duplicate path. Add a client-side backstop so an unresolvable dependency drops the affected operations and tells the volunteer instead of jamming the queue.

### 3. [HIGH] Permanently deleting an email deletes unrelated files that happen to have identical contents

- **Where:** [emails/controller.ts:430-455](apps/backend/src/app/modules/emails/controller.ts#L430-L455), against the deduplication rule at [email-ingester.service.ts:277-292](apps/backend/src/app/modules/emails/services/email-ingester.service.ts#L277-L292).
- **Trigger:** Someone attaches a document to an email that is also stored elsewhere in the workspace — a file uploaded on the Files page, an avatar, a newsletter image, a bug-report screenshot — and later empties that email from the trash.
- **What breaks:** Attachments are deduplicated by content hash against the tenant's _entire_ `files` table, so an email attachment can end up pointing at a row that something else created. `purgeOrphanedFiles` then asks only "is any remaining email attachment still using this file?" ([:436-444](apps/backend/src/app/modules/emails/controller.ts#L436-L444)). If the answer is no it deletes the `files` row and the stored blob ([:455-463](apps/backend/src/app/modules/emails/controller.ts#L455-L463)). The avatar, newsletter image or Files-page entry that pointed at the same row is gone permanently — the blob deletion happens outside the transaction and nothing keeps a copy.
- **The reverse direction is worse than a mirror image.** `FilesController.delete` ([files/controller.ts:145-161](apps/backend/src/app/modules/files/controller.ts#L145-L161)) deletes the row and the blob with **no reference check of any kind**, and avatar replacement does the same thing inline ([auth/controller.ts:1961-1978](apps/backend/src/app/modules/auth/controller.ts#L1961-L1978)). After either, an email attachment download reports the file as missing.
- **The obvious fix does not work.** The `entity_type`/`entity_id` columns on `files` are populated **only** by `registerFile` ([files/controller.ts:136-137](apps/backend/src/app/modules/files/controller.ts#L136-L137)). The three attachment insert sites ([email-ingester.service.ts:517-527](apps/backend/src/app/modules/emails/services/email-ingester.service.ts#L517-L527), [emails-api.route.ts:269-281](apps/backend/src/app/modules/emails/routes/emails-api.route.ts#L269-L281), [attachment-materializer.ts:173-186](apps/backend/src/app/modules/emails/services/attachment-materializer.ts#L173-L186)) and the avatar upload ([auth/controller.ts:1981-1993](apps/backend/src/app/modules/auth/controller.ts#L1981-L1993)) set neither column. A check based on `entity_type`/`entity_id` alone would still delete an avatar.
- **The database will not catch it either.** Seven columns point at `files`, and five have no foreign key at all: `bug_reports.screenshot_file_id` ([schema.sql:229](apps/backend/src/app/_migrations/schema.sql#L229)), `companies.file_id` ([:423](apps/backend/src/app/_migrations/schema.sql#L423)), `households.file_id` ([:1629](apps/backend/src/app/_migrations/schema.sql#L1629)), `persons.file_id` ([:2356](apps/backend/src/app/_migrations/schema.sql#L2356)) and `tasks.file_id` ([:2789](apps/backend/src/app/_migrations/schema.sql#L2789)). Only `email_attachments.file_id` ([:7189](apps/backend/src/app/_migrations/schema.sql#L7189)) and `profiles.avatar_file_id` ([:8533](apps/backend/src/app/_migrations/schema.sql#L8533)) have one, and both are `ON DELETE SET NULL`.
- **What on-call sees:** Nothing at deletion time. Later, a broken avatar or an image that stopped rendering, with no error trail.
- **Blast radius:** One workspace per occurrence; silent, permanent loss of content the user uploaded.
- **Confidence:** High. Both code paths, all four insert sites and every foreign key read directly. The existing test (`emails/controller.delete-cleanup.spec.ts`) covers only a file shared between two emails, which is why the non-email owner was missed.
- **Fix sketch:** Three options, in increasing cost: narrow the dedup so an email attachment only ever reuses a file that is itself an email attachment; enumerate every referencing column in the purge check and in `FilesController.delete`; or add an explicit reference count on `files` maintained by every writer.

### 4. [HIGH] Merging two people silently unlinks the source person's tasks and leaves a volunteer access row pointing at a deleted person

- **Where:** [persons.repo.ts:857-896](apps/backend/src/app/modules/persons/repositories/persons.repo.ts#L857-L896), with the missed foreign key at [schema.sql:7973](apps/backend/src/app/_migrations/schema.sql#L7973).
- **Trigger:** Any duplicate merge where the source person has tasks, a companion volunteer record, a workflow run, or a turf assignment.
- **What breaks:** The merge re-points the child rows whose foreign keys would otherwise be nulled or cascade-deleted when the source person is removed, and its own comment names them: donations, pledges, delivery requests, delivery routes, turf knocks, form submissions. Nineteen foreign keys reference `persons`; seven of those are `ON DELETE SET NULL`; six are re-pointed. `tasks.person_id` ([schema.sql:7973](apps/backend/src/app/_migrations/schema.sql#L7973)) is the `SET NULL` reference the merge never touches, so those tasks quietly lose their contact when the source row is hard-deleted.
- **Three more person-referencing columns are unhandled and have no foreign key at all**, so the database does not null them either — after the merge they hold the id of a row that no longer exists:
  - `companion_volunteers.person_id` ([schema.sql:514](apps/backend/src/app/_migrations/schema.sql#L514)), `NOT NULL`, with `UNIQUE (tenant_id, person_id)` at [:4867](apps/backend/src/app/_migrations/schema.sql#L4867). This is the volunteer access-control table: the row keeps working after the merge, granting a device session against a person who is gone.
  - `workflow_runs.person_id` ([schema.sql:3391](apps/backend/src/app/_migrations/schema.sql#L3391)).
  - `turf_assignments.volunteer_person_id` ([schema.sql:2951](apps/backend/src/app/_migrations/schema.sql#L2951)).
- **What on-call sees:** Nothing. Someone later asks why a task no longer shows the person it was about, or why a revoked volunteer's link still works.
- **Blast radius:** Per merge, unrecoverable without a database restore. Merging is not reversible and the source row is gone.
- **Confidence:** High. The merge read end to end and every foreign key and `person_id` column read from the schema. The rest of the merge is sound: one transaction, every table tenant-scoped, and consent flags combined in the most restrictive direction ([persons.repo.ts:992-1032](apps/backend/src/app/modules/persons/repositories/persons.repo.ts#L992-L1032)).
- **Fix sketch:** Add `tasks`, `workflow_runs` and `turf_assignments` to the re-pointing block. `companion_volunteers` cannot be blind-updated because of its unique constraint — it needs the keep-the-target, delete-the-source treatment the merge already uses for `campaign_person_facts` ([persons.repo.ts:901-921](apps/backend/src/app/modules/persons/repositories/persons.repo.ts#L901-L921)). Add a test, but make it enumerate **columns that name a person**, not foreign-key constraints: a constraint-based test would have caught `tasks.person_id` and missed all three of the columns that have no constraint.

### 5. [MEDIUM-HIGH] An unauthenticated public form submission can rewrite an existing contact's address, notes, name and mobile number

- **Where:** [web-forms/controller.ts:448-473](apps/backend/src/app/modules/web-forms/controller.ts#L448-L473), with the address block at [:382-386](apps/backend/src/app/modules/web-forms/controller.ts#L382-L386) and notes at [:343](apps/backend/src/app/modules/web-forms/controller.ts#L343).
- **Trigger:** Anyone who knows a tenant's public form address and the email address of someone in that tenant's contacts. The only limit is five submissions per minute per source address ([controller.ts:31-32](apps/backend/src/app/modules/web-forms/controller.ts#L31-L32), enforced at [:145](apps/backend/src/app/modules/web-forms/controller.ts#L145)), counted in an in-process map that resets on every deploy.
- **What breaks:** The person is matched on the submitted email address alone ([:439-444](apps/backend/src/app/modules/web-forms/controller.ts#L439-L444)). The handler then:
  - re-points that person's `household_id` at a household the submitter just created with an address of their choosing ([:457-459](apps/backend/src/app/modules/web-forms/controller.ts#L457-L459));
  - appends the submitted notes to the person's existing notes ([:460-464](apps/backend/src/app/modules/web-forms/controller.ts#L460-L464)) — an unbounded `text` column, appended on every submission and never replaced;
  - fills in a blank first name, last name **or mobile number** from the submitted values ([:454-456](apps/backend/src/app/modules/web-forms/controller.ts#L454-L456)).
- **The payload is not filtered against the form's configured field list.** The address fields and the notes field are read straight out of `payload`, so the address injection and the household re-point work against a form that renders no address inputs at all. The payload itself is a plain string map taken from the request body with no schema, no field-count limit and no length limit on any value; the only ceiling on the path is the global 1 MiB request-body limit ([fastify.server.ts:53](apps/backend/src/fastify.server.ts#L53)).
- **Every submitted key is persisted verbatim.** [:662-677](apps/backend/src/app/modules/web-forms/controller.ts#L662-L677) copies the whole payload (minus the honeypot key) into `form_submissions.answers`.
- **The audit trail names a real staff member for an anonymous edit.** `const creatorId = String(form.createdby_id)` ([:362](apps/backend/src/app/modules/web-forms/controller.ts#L362)) is used as `createdby_id`/`updatedby_id` on every row written, and as the `user_id` on the `user_activity` row ([:645-658](apps/backend/src/app/modules/web-forms/controller.ts#L645-L658)).
- **What on-call sees:** Nothing. A staff member eventually reports that a supporter's address is wrong or their notes are full of junk.
- **Blast radius:** Any contact in any workspace that has a published form, one at a time.
- **Confidence:** High for the code path. How much text a row can accumulate before the interface degrades is an inference, not something measured.
- **Fix sketch:** Validate the payload with a schema that bounds field count and value length, and restrict it to the form's configured fields. Treat matching an existing person as a link, not a licence to edit: do not re-point the household. The submitted notes are **already** recorded on the submission at `:662-677`, so appending them to `persons.notes` is pure duplication and the append can simply be deleted. Attribute the write to the anonymous submission rather than to the form's creator.

### 6. [MEDIUM-HIGH] Any signed-in caller can ask for ten million rows, and three endpoints will return the whole table for an empty request

- **Where:** [core.schema.ts:99-107](libs/common/src/lib/schemas/core.schema.ts#L99-L107) bounds the two paging fields separately; [base.repo.ts:461-476](apps/backend/src/app/lib/base.repo.ts#L461-L476) turns their difference into the SQL limit with no clamp.
- **Trigger:** Any authenticated caller — including a viewer, since these are reads — sends `startRow: 0, endRow: 10000000` to a grid or feed endpoint. Or, for the second half below, sends no paging fields at all.
- **What breaks:** Each field is capped at ten million ([core.schema.ts:99-100](libs/common/src/lib/schemas/core.schema.ts#L99-L100)), but the _span_ between them is not, and the span is what becomes the limit ([base.repo.ts:466](apps/backend/src/app/lib/base.repo.ts#L466)). The 5,000-row backstop applies only when no end row is supplied at all; the comment at [:469-472](apps/backend/src/app/lib/base.repo.ts#L469-L472) says "untrusted input is already bounded by getAllOptions", which is true per field and not true of the difference.
- **"Clamp it in the one place it is computed" is not available.** Sixteen places compute the span and exactly one clamps it — [households.repo.ts:392-397](apps/backend/src/app/modules/households/repositories/households.repo.ts#L392-L397), which wraps the subtraction in `Math.min(..., MAX_PAGE_SIZE)`. The fifteen unclamped ones are [base.repo.ts:466](apps/backend/src/app/lib/base.repo.ts#L466), [user-activity.repo.ts:116](apps/backend/src/app/lib/user-activity.repo.ts#L116) and [:168](apps/backend/src/app/lib/user-activity.repo.ts#L168), and the repositories for persons, lists, teams, tags, authusers, newsletters, workflows, workflow-enrollments, web-forms, delivery-requests, events and volunteer-events.
- **Worse: three of them apply no limit at all when both paging fields are omitted**, because the limit sits inside a `$if` on both fields being numbers and these queries never reach `applyOptions` — [persons.repo.ts:433-434](apps/backend/src/app/modules/persons/repositories/persons.repo.ts#L433-L434), [events.repo.ts:85-86](apps/backend/src/app/modules/events/repositories/events.repo.ts#L85-L86), [volunteer-events.repo.ts:96-97](apps/backend/src/app/modules/volunteer-events/repositories/volunteer-events.repo.ts#L96-L97). `persons.getAllWithAddress` is directly callable as a plain authenticated procedure ([persons/trpc.router.ts:97-98](apps/backend/src/app/modules/persons/trpc.router.ts#L97-L98), registered at [:295](apps/backend/src/app/modules/persons/trpc.router.ts#L295)) and with empty input returns every person in the tenant across seven left joins ([persons.repo.ts:176-191](apps/backend/src/app/modules/persons/repositories/persons.repo.ts#L176-L191)) with no `LIMIT`. That is a cheaper request to make and a larger read than the ten-million-row path.
- **The activity router's unvalidated paging is a different problem than it looks.** [activity/trpc.router.ts:15-16](apps/backend/src/app/modules/activity/trpc.router.ts#L15-L16) validates `startRow`/`endRow` as bare `z.number()` with no integer, minimum or maximum constraint, and they reach [user-activity.repo.ts:167-168](apps/backend/src/app/lib/user-activity.repo.ts#L167-L168). Negative and fractional values arrive at PostgreSQL as bound parameters and produce a query **error** (`LIMIT must not be negative`, `invalid input syntax for type bigint`), not an unbounded read. It is a source of 500-level noise, not exposure.
- **What on-call sees:** A memory spike or a container killed for exceeding its memory limit. The first review established that such a kill takes every in-flight background job with it, because the API and the worker share one process.
- **Confidence:** High; all cited lines read directly.
- **Fix sketch:** Clamp the derived limit to `MAX_PAGE_SIZE` in `base.repo.ts` and in each of the fourteen hand-written repositories, and make the limit unconditional in the three that skip it entirely. Give the activity and notification routers the same bounded paging schema everything else uses.

### 7. [MEDIUM-HIGH for Microsoft mailboxes, LOW-MEDIUM for Gmail] A message the user merely archives or moves is hard-deleted from the CRM, taking the team's comments and assignment with it

- **Where:** [email-ingester.service.ts:125-169](apps/backend/src/app/modules/emails/services/email-ingester.service.ts#L125-L169), reached from [ms-sync.service.ts:190-197](apps/backend/src/app/modules/ms-sync/ms-sync.service.ts#L190-L197) and [google-sync.service.ts:175-196](apps/backend/src/app/modules/google-sync/google-sync.service.ts#L175-L196).
- **What breaks:** `deleteMessage` is unconditional and permanent. In one transaction it removes the rows in `email_comments`, `email_bodies`, `email_headers`, `email_recipients`, `email_attachments`, `email_trash` and `emails` ([:142-165](apps/backend/src/app/modules/emails/services/email-ingester.service.ts#L142-L165)), then deletes the body blob and any newly orphaned attachment files. Everything the CRM itself added — internal comments, the assigned staff member, the open/closed triage status, the favourite flag — goes with it. The `emails` table has a `deleted_at` column for soft deletion ([schema.sql:1345](apps/backend/src/app/_migrations/schema.sql#L1345)) that this path does not use, and no activity-log entry is written.
- **The Microsoft half is a live per-sync data-loss path, not a decision item.** The `@removed` branch at [ms-sync.service.ts:190-197](apps/backend/src/app/modules/ms-sync/ms-sync.service.ts#L190-L197) runs on every sync, initial or incremental, over a per-folder delta. A folder-scoped Microsoft Graph delta marks a message `@removed` when it leaves that folder — moved, archived, or filed by a rule — not only when it is deleted. Ordinary mailbox housekeeping therefore destroys the CRM's copy on the next incremental sync.
- **The Gmail half is narrower.** Its sweep is gated on `if (folderLastSync === 0)` ([google-sync.service.ts:175](apps/backend/src/app/modules/google-sync/google-sync.service.ts#L175)), so it runs only on a first connection or a forced re-sync. On a genuine first connection there is nothing local to delete, so the practical trigger is a forced re-sync of an established mailbox.
- **Blast radius:** Per message, per Microsoft sync cycle. Per forced re-sync for Gmail.
- **Confidence:** High on the code. The Microsoft delta's treatment of a folder move is documented provider behaviour, not something read from this repository.

So the build, migrate and deploy jobs — which run dependency installs and hold the Azure credentials, the Cloudflare token and the production database owner password — get whatever the repository default is. The actual exposure depends on a repository setting that cannot be read from the code.
- **The edge proxy aborts the whole exchange at 30 seconds**, including the request upload ([pplforms-edge/src/index.ts:75](infra/pplforms-edge/src/index.ts#L75) and [:86](infra/pplforms-edge/src/index.ts#L86); [go-edge/src/index.ts:39](infra/go-edge/src/index.ts#L39) and [:49](infra/go-edge/src/index.ts#L49)), and converts the abort into the same "temporarily unreachable" response a real outage produces ([pplforms-edge/src/index.ts:134-140](infra/pplforms-edge/src/index.ts#L134-L140)). **Aborting the worker's fetch does not cancel the backend's work.** If a form submission runs past 30 seconds, the database transaction may already have committed and a Stripe Checkout session may already exist, while the visitor is told the service is unreachable and will most likely resubmit. There is no idempotency key anywhere on that path — the string does not appear in `modules/web-forms/` or `modules/donations/`. No public or companion screen uploads a file, so the upload half of the timeout is not currently reachable.

### 20. Smaller findings, grouped

Each of these is real and read in the source, but is either narrow, needs a product decision, or is latent rather than currently firing.

**Authentication**

- **Changing your own email address twice before verifying permanently demotes an owner to viewer.** On a self email change, [auth/controller.ts:1807-1811](apps/backend/src/app/modules/auth/controller.ts#L1807-L1811) saves the **current** row's email and role as `previous_email`/`previous_role` and sets `role = 'viewer'`. On a second self-change before verifying, the current row already holds `viewer`, so `viewer` becomes the saved previous role, and `verifyEmail` restores it ([:2163](apps/backend/src/app/modules/auth/controller.ts#L2163)). The owner is now a viewer with no record of what they were. In a multi-user workspace, `ensureAtLeastOneOwner` ([:713-754](apps/backend/src/app/modules/auth/controller.ts#L713-L754), called at [:1853](apps/backend/src/app/modules/auth/controller.ts#L1853)) stops recognising them as an owner — its "still counts as an owner" clause matches `role = 'viewer' AND previous_role = 'owner'` ([:723-725](apps/backend/src/app/modules/auth/controller.ts#L723-L725)), which no longer holds — and silently promotes the oldest other account to owner. A solo owner instead gets `BadRequestError('The system must have at least one owner.')` and a rolled-back transaction, while remaining a viewer from the first change. This is reachable from the ordinary profile page, because a self email change deliberately does **not** clear the session ([:1862-1864](apps/backend/src/app/modules/auth/controller.ts#L1862-L1864)).
- **A user can change their account's email address and stay marked as verified.** Changing the address sets the verified flag to false at [auth/controller.ts:1805](apps/backend/src/app/modules/auth/controller.ts#L1805); line [1830](apps/backend/src/app/modules/auth/controller.ts#L1830) then writes the client-supplied `verified` value over it. The guard at [:1770-1772](apps/backend/src/app/modules/auth/controller.ts#L1770-L1772) does not catch this because it only rejects a value that _differs_ from the stored one, and on an already-verified account sending `true` is not a change. Nothing we ship sends the field, so this needs a hand-made API call. Fix: drop `verified` from the update schema ([auth.schema.ts:92](libs/common/src/lib/schemas/auth.schema.ts#L92)); nothing legitimately sets it.
- **A refresh token replayed inside the 60-second grace window mints a second, independent session.** A rotated session's refresh token stays honoured for `ROTATION_REUSE_GRACE_MS` ([auth/controller.ts:1069-1074](apps/backend/src/app/modules/auth/controller.ts#L1069-L1074); the constant is 60 seconds, [:2745](apps/backend/src/app/modules/auth/controller.ts#L2745)) so concurrent tabs do not strand each other. Within that window the same token can be replayed repeatedly, and each replay calls `createTokens` ([:1105-1110](apps/backend/src/app/modules/auth/controller.ts#L1105-L1110)), which **inserts a new `sessions` row without deleting anything** ([auth-tokens.ts:26](apps/backend/src/app/modules/auth/auth-tokens.ts#L26) only deletes when an `oldSession` is passed, and this call passes none; the insert is at [auth-tokens.ts:49](apps/backend/src/app/modules/auth/auth-tokens.ts#L49)). The `markRotated` call is skipped because the session is already rotated ([:1111-1113](apps/backend/src/app/modules/auth/controller.ts#L1111-L1113)). So a thief who replays within 60 seconds of the victim's rotation gets an independent valid session, the victim's session keeps working, and no log line is produced at all. There is no session-list or "sign out other devices" screen anywhere in the frontend, so the victim cannot see or kill it; the only remedy is a password reset.
- **A late re-used refresh token is rejected but nothing actionable is recorded.** Beyond the grace window the attempt just fails with `UnauthorizedError` ([auth/controller.ts:1071-1073](apps/backend/src/app/modules/auth/controller.ts#L1071-L1073)) — whoever refreshed first keeps their session and the other party is signed out; if that is the attacker, the legitimate user is the one ejected. Saying "nothing is logged" would be literally wrong: every tRPC error passes through `logger.error` at [trpc.ts:18](apps/backend/src/trpc.ts#L18). But what is written is a bare `UnauthorizedError`, indistinguishable from an expired cookie, an idle timeout or a missing cookie, and only 500s reach Sentry ([trpc.ts:43-45](apps/backend/src/trpc.ts#L43-L45)) — so there is no signal anyone could alert on. Fix: revoke every session for that user on a late re-use, and log it distinctly.
- **Password-reset and verification mail is limited only by the in-process counter** ([auth/trpc.router.ts:68-79](apps/backend/src/app/modules/auth/trpc.router.ts#L68-L79)), against the rule stated in the durable limiter's own header: use the durable one "whenever exceeding the limit costs real money or reputation: paid API calls, SMS, and outbound mail." The "not shared between replicas" half of this is currently moot — the container runs at min 1 / max 1. What survives is that the counters reset on every deploy and every container restart, so the practical exposure is roughly three reset emails per hour per address, plus three more after each deploy. Note also that the durable limiter fails **open** on a database error ([durable-rate-limiter.ts:81-84](apps/backend/src/app/lib/durable-rate-limiter.ts#L81-L84)), so switching these call sites to it does not make them fail-closed.

**Mailbox sync**

- **The Gmail deletion sweep compares two different clocks.** The local candidate rows are selected on the `Date:` header ([google-sync.service.ts:186](apps/backend/src/app/modules/google-sync/google-sync.service.ts#L186), set from the header at [:241-256](apps/backend/src/app/modules/google-sync/google-sync.service.ts#L241-L256)), while the server list comes from a Gmail query whose `after:` operator filters on Gmail's own `internalDate`. A message whose header date is later than its received time — sender clock skew, wrong time zone, or spam with a forged date — is a deletion candidate the server query can never return, so it is deleted locally while still in the mailbox. This repeats on every forced re-sync. The Microsoft sync stores and filters the same value and does not have this problem.
  The obvious fix, "store `internalDate` and filter on that", is insufficient as written: `date_sent` is also the inbox sort key and the timestamp shown to users ([email.repo.ts:123](apps/backend/src/app/modules/emails/repositories/email.repo.ts#L123) orders on it, and the comments at [:97](apps/backend/src/app/modules/emails/repositories/email.repo.ts#L97) and [:121](apps/backend/src/app/modules/emails/repositories/email.repo.ts#L121) record that it is deliberately denormalized onto `emails` to keep the sort indexable). Overwriting it changes what Gmail users see. It needs a separate column plus a migration and a backfill, and a null provider timestamp must mean "not a deletion candidate".

**Companion apps**

- **A server-rejected operation deletes the volunteer's recorded work from the phone** ([canvass-store.ts:708-713](apps/companion/src/app/canvass/canvass-store.ts#L708-L713)) — removed from the queue and the overlay, with one dismissable message as the only notice, and flushes run automatically when connectivity returns. Fix: move rejected work to a list the volunteer can see and retry.
- **Queued data stays on the phone after access is revoked** — `expireSession` clears the session token and sets a flag but leaves the queue in place ([canvass-store.ts:732-735](apps/companion/src/app/canvass/canvass-store.ts#L732-L735)) — **and restoring the queue silently discards any entry that no longer matches the current operation format** ([canvass-store.ts:815-827](apps/companion/src/app/canvass/canvass-store.ts#L815-L827)), so a future change to that format would erase a stored offline shift with no message.

## Areas checked that turned up nothing worth reporting

- **Authentication, apart from the items in finding 20.** The sign-in, two-factor, password-reset, email-verification, token-renewal, invitation, user-update and user-deletion paths of the 2,748-line controller and its whole router were read. Sign-in runs a password comparison even for an unknown address so a missing account and a wrong password cost the same; the per-account failure counter is the durable database-backed one; one-time codes are cryptographically generated, stored hashed, compared in constant time ([controller.ts:2032-2039](apps/backend/src/app/modules/auth/controller.ts#L2032-L2039)), capped at five wrong guesses and then invalidated; the refresh token never appears in a response body; privilege changes are denied by default and an administrator cannot promote themselves, demote an owner, or remove the last one; deleting a user writes a tombstone rather than a row deletion, because sixty-nine foreign keys point at `authusers`. Two enumeration oracles remain and are documented in the code as accepted decisions, both bounded on two axes.
- **Signed download and upload links.** Tokens are scoped to one file or one email plus one tenant, verified against the requested id, and separated by purpose. Upload keys are round-tripped as a signed handle specifically so a client can never name the storage key it writes to.
- **Blob storage.** The account-wide cross-origin policy grants only `PUT` and `OPTIONS` from the application's own origin; write links last fifteen minutes; storage keys are server-derived and filenames sanitized on the Files path.
- **Money handling.** Amounts are integer cents throughout; `donations.amount` is an `integer NOT NULL` column. Mock payment paths require an explicit environment opt-in, not merely an absent Stripe key.
- **Zapier API keys.** 32 random bytes, stored as a hash, never retrievable, looked up by hash, with a plan gate at the single lookup point and outbound webhook URLs re-validated before each request with redirects disabled and a timeout.
- **Duplicate detection, notifications cross-tenant safety, person connections, and the public form tenant resolution and error handling** were each checked and are correct; the public form path escapes every interpolation and never returns internal error text ([web-forms-public.route.ts:570-576](apps/backend/src/app/modules/web-forms/routes/web-forms-public.route.ts#L570-L576)).
- **The two Cloudflare Workers, apart from findings 15, 16 and 19.** Neither caches anything — no use of the cache API and no rewriting of cache headers in either direction — and the two long-lived caches the backend does set are marked private, which shared caches must not store. Neither worker can be made to fetch a client-chosen host: the target is always a fixed configured origin plus an already-normalized path, and a percent-encoded traversal attempt survives as an encoded slug and produces a 404. The refresh-token cookie is host-only for the API hostname, so browsers never send it to either worker origin; the only cookie that reaches them is the non-secret "a session exists" hint. Credentials are forwarded only to the fixed backend origin. The authenticated tRPC surface is mounted at the root rather than under the proxied path, so it never passes through the edge at all.
- **The container image and its probes.** It runs as an unprivileged user with correctly owned files. The three health probes described in the checklist match the endpoints the application actually serves, including the deliberate choice to point liveness at a route that does not touch the database, so a database outage does not cause a restart loop. No literal credential appears anywhere in the infrastructure files or workflows; every secret is a reference, and the one place a key is used as a search pattern prints only a count.
- **The marketing website.** No forms, no third-party scripts, no analytics, no secrets, nothing that writes HTML into the page. Its only network call is a same-origin proxy to a public currency-rate service whose response is filtered before use. Four categories of number the site states — the two paid plan prices, the bounce and complaint thresholds, the per-plan sending allowances, and the cookie list — all still match the code that backs them.

## Two open questions from the first review, now answered

**"Is the donation amount always present on a Checkout Session?" — yes, and the concern is closed.** There is a second place that creates a donation Checkout Session outside the Stripe processor, at [donations/controller.ts:405](apps/backend/src/app/modules/donations/controller.ts#L405), which the first review did not know about. It is the monthly recurring session, and it marks itself with `isRecurring: 'true'` in the session metadata ([:486](apps/backend/src/app/modules/donations/controller.ts#L486)). The webhook worker branches on exactly that flag ([webhook-worker.ts:347-354](apps/backend/src/app/lib/jobs/webhook-worker.ts#L347-L354)), so a recurring session can never reach the branch that reads the one-time amount. One-time sessions are created only by the processor, which always sets it. No change needed.

**"Are there other source files containing NUL bytes?" — no.** Every TypeScript, HTML, JavaScript and CSS file under the frontend, both companion apps, the website and the shared component library was checked; none is classified as binary.

**"What is the container memory limit?" — 1 GiB, and it is not declared anywhere in code.** See finding 17. This sharpens the first review's import-handler finding and finding 6 above: both are bounded by 1 GiB shared between the API and the background worker in one process.

Also confirmed while reading the schema: row-level security is enabled on 81 tables, and every policy permits everything when no tenant is bound to the connection. That is the documented, intended design for background workers, and it means the tenant-scoping lint rule — not the database — is the real protection in worker code.

## Now settled from code

Six items that were open questions when this review was drafted have since been answered by reading the source. They are recorded here rather than in the uncertainty register below.

1. **What is stored in the saved grid state?** Typed filter values, verbatim — see the grid item in finding 20. The leak between users on a shared computer is real.
2. **Can a public form accept a file?** No. `FormFieldObj.type` is `z.enum(['text', 'area', 'select', 'checks'])` ([web-forms.schema.ts:69](libs/common/src/lib/schemas/web-forms.schema.ts#L69)); the SPA renders only `input`, `textarea`, `select` and checkbox controls; and no `type="file"`, `FormData` or multipart usage exists anywhere in the companion app or the public forms UI. The upload half of the 30-second edge abort (finding 19) is therefore not currently reachable.
3. **Does anything we ship send a `verified` field to the user-update endpoint?** Nothing in the repository does — the frontend, the companion app, the website, the scripts and the seeds were all searched. Only two backend specs send it, at [trpc.router.spec.ts:731](apps/backend/src/app/modules/auth/trpc.router.spec.ts#L731) and [:794](apps/backend/src/app/modules/auth/trpc.router.spec.ts#L794), and both assert that the guard rejects a changed value.
4. **Does anything queue an export without a column list?** No grid sets `exportEntity: 'users'` — the only values in the frontend are `lists`, `households`, `persons` and `companies`. The point is moot, though, because the `columns` list is itself unvalidated (finding 1), so an explicit list is the stronger attack.
5. **Does Outlook report a folder move as a removal?** Yes. A folder-scoped Microsoft Graph delta marks a message `@removed` when it leaves that folder, so finding 7's Microsoft half is a live per-sync data-loss path rather than a rare one.
6. **Does Gmail's `after:` filter on receipt time or on the message's own date header?** On receipt time — `after:` filters on Gmail's `internalDate`. The two-clock mismatch in the Gmail sweep (finding 20) is therefore real, and it repeats on every forced re-sync for any message with a future `Date:` header.

## Uncertainty register

1. **Do requests arriving through a Cloudflare Worker reach the backend with the visitor's address or Cloudflare's?** (finding 16). If Cloudflare's, then every per-address limit on the public donation pages, form pages, volunteer endpoints and canvassing endpoints is a single shared bucket across all tenants.
