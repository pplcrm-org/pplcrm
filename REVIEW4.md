# Fourth production-risk review — the surface no prior review ever read

Read-only review. No code was changed by it.

`REVIEW.md`, `REVIEW2.md`, and `REVIEW3.md` hold the first three reviews. All of
REVIEW3's high and medium findings were fixed and committed (`15f9b047..14d64215`)
before this pass began. This review reads what none of the three earlier passes
opened, as listed in REVIEW3's own "coverage gaps" section:

1. The donation-receipt PDF renderers and the timezone date arithmetic.
2. The workflow (automation) enrollment side — triggers, conditions, step editing.
3. The billing controller's checkout, portal, and Stripe-reconciliation paths.
4. The imports, settings, and campaigns backend modules.
5. The electoral-boundary write paths.
6. The unreviewed frontend experiences (donations detail, receipts ledger, the
   session-management screen, canvassing, deliveries, the import wizard).
7. The companion volunteer apps, the shared UI controls, and the demo seeder.
8. An independent adversarial re-read of the five commits that fixed REVIEW3.

Eight focused sub-reviews ran in parallel. Every finding below carries a file-and-line
reference read in the source by its reviewer; the orchestrator re-opened and confirmed
the **top claim of each area at the cited line** before including it. Two findings
(the printed-date shift and the torn PDFs) were additionally verified by executing the
relevant library code in isolation, not only by reading. Where a claim was not
re-verified, the finding's confidence note says so.

**Calibration, as directed by the maintainer:** this review reports what real tenants,
donors, and volunteers will plausibly hit — data loss, wrong documents, dead-end flows,
silent failure. It does not report hostile-precision race conditions, style issues, or
fit-and-finish polish. Test files were deliberately not reviewed.

**Every finding carries two risk lines** so each can be decided individually:

- **If left:** what actually happens to users if nothing is done.
- **If fixed:** what the fix touches and what could regress.

## Tier 1 — fix before launch

Ordinary paths, real harm, and in every case the fix is small relative to the harm.

### T1-1. Every gift date printed on every donation PDF is one day early on a UTC server — and production is UTC

- **Where:** `torontoDateString` (apps/backend/src/app/lib/pdf/pdf-common.ts:40-47) re-formats a JS Date in Toronto time. Postgres `date` columns (`gift_date` on receipts and receipt items) come back from the `pg` driver as **server-local midnight**; on a UTC server, re-formatting that instant in Toronto shifts it back one day. Call sites: receipts/controller.ts:1142 (acknowledgement), :1184 (per-gift receipt), :1185 (cumulative items table), :1351 (statement rows). The acknowledgement also derives its "official receipt for YYYY follows" promise from the shifted string.
- **Verified:** mechanism reproduced against the installed pg/pg-types modules; no custom date parser exists in the repo; no `TZ` is set in the Dockerfile, bicep, or deploy workflow. Stored dates are **correct** — only rendering is wrong, so no data repair is needed. A January 1 gift prints as December 31 of the **prior tax year**. Developer machines on Toronto time can never reproduce it.
- **If left:** every tax document and giving statement misstates its gift dates; year-boundary gifts claim the wrong tax year on a legal document.
- **If fixed:** four call sites plus one helper (select the columns as text, or format by local components); set `TZ=UTC` in the Dockerfile so behavior stops depending on the host. The one regression to guard: do not apply the new date-column formatter to real timestamps (`issued_at`) — name the helpers unmistakably.
- **Recommendation: fix.** Highest harm-to-effort ratio in this review.

### T1-2. The "New subscriber" / "New unsubscriber" automation triggers never fire for real signups or real unsubscribes

- **Where:** the only caller of `triggerSubscriptionChanged` is the staff consent toggle (campaigns/controller.ts:348 — verified by grep). The public form opt-in (web-forms/controller.ts:681), the double-opt-in confirmation (:946), and the one-click unsubscribe (unsubscribe.route.ts:167) all write subscription state and fire nothing.
- **If left:** the shipped "Welcome series" starter recipe — built on `new_subscriber` — sits active with zero runs and no error for every tenant whose supporters sign up the normal way. The win-back/goodbye counterpart never sees a real unsubscribe.
- **If fixed:** three files, ~30 lines. Two care points: fire only when the row lands `subscribed` (not `pending`), and wrap the unsubscribe-route call in its own try/catch — that route is public and its write must never fail because enrollment failed. The form-path call runs inside the submission transaction, which interacts with T2-10 below.
- **Recommendation: fix.**

### T1-3. Editing a live automation's steps corrupts everyone mid-sequence

- **Where:** `saveSteps` deletes and re-inserts all steps, renumbering by array position (workflows/controller.ts:104-133); each enrollment stores only a step _number_ (workflows.handlers.ts:166-177). Insert a step above someone → they receive an email twice. Delete a middle step → they skip one. Shorten the sequence → they are silently marked completed.
- **If left:** any edit of an automation with people in it misdelivers, with no warning; wait steps make the exposure window days long. The editor is explicitly built for insertion and drag-reorder.
- **If fixed:** two options. Diff-and-remap `current_step_number` on save — contained to `saveSteps` but subtle for reorders. Or give enrollments a `current_step_id` and make saves update-not-recreate — sturdier; a migration plus ~4 files. Either way, warn in the editor when active enrollments exist.
- **Recommendation: fix (remap version + editor warning is the pragmatic scope).**

### T1-4. A phone-only contact row destroys its entire 100-row import batch

- **Where:** the import's blank-address test counts `home_phone` as an address field (persons.service.ts:930-939 — verified), so a row with only a phone gets no household created, then `household_id: ''` on a `NOT NULL bigint` (:1213 — verified) rolls back the whole 100-row chunk. Outlook and Google contact exports auto-map "Home Phone" and are full of such rows.
- **If left:** the first thing a real workspace does — import its contacts — quietly loses up to 100 good rows per bad one and still reports "completed".
- **If fixed:** three lines in one function (treat phone-only as address-less; widen the blank-household condition). Behavior change: phone-only contacts join the shared blank household, which is what should have happened.
- **Recommendation: fix.**

### T1-5. A failed import batch loses rows with no record of which, and the import still says success

- **Where:** the chunk-failure catch (persons.service.ts:1384-1390) counts errors but writes no skip reasons, the returned error messages are ignored by the job handler (import.handlers.ts:208), and status is set `completed` regardless (:233). Households importer is the same and never writes skip reasons at all. A rolled-back chunk also double-counts rows as both skipped and errored.
- **If left:** any partial failure (T1-4 today; any deadlock or constraint tomorrow) silently loses data behind a success message — the worst kind of import failure.
- **If fixed:** low risk, confined to the two `processImportRows` methods plus the history display: per-row skip reasons in the catch, write the error messages, optionally a `completed_with_errors` status.
- **Recommendation: fix, together with T1-4.**

### T1-6. Imports above ~1 MiB of request body fail with an unexplained transport error

- **Where:** server-wide `bodyLimit: 1 MiB` (fastify.server.ts:53) vs. an import mutation that accepts 5,000 rows _plus the entire raw CSV_ in the same request (import-wizard.ts:470-479). Realistic ceiling ≈ 3,000 rows; the wizard has no size or row-count guard, and a Fastify 413 is not a tRPC error, so the user sees a raw message. The wizard also never checks `MAX_IMPORT_ROWS` (5,000), so a 20,000-row voter file survives all the mapping work and dies at the very end.
- **If left:** purchased voter files — the core import case for this product — cannot be imported, with no explanation.
- **If fixed:** two independent pieces. (a) Client-side guards: refuse over 5,000 rows at the upload step with a "split the file" message, and pre-check payload size — a few lines, near-zero risk, converts opaque failure into a clear one. (b) Stop sending `source_csv` inline (upload it separately) to actually raise the ceiling — medium: touches the wizard, four import mutations, and the download route.
- **Recommendation: do (a) now; schedule (b).**

### T1-7. The gift page treats a donor's year-end giving statement as that gift's own tax receipt

- **Where:** `taxReceipts` filters only `kind !== 'acknowledgement'` (donation-view.ts:80 — verified; the comment above it even claims "Official tax receipts only"). Statements cover gifts via receipt items, so they appear on every covered gift. Consequences: "Issue receipt" disappears for any statement-covered gift; **Cancel on the statement row succeeds and voids the donor's whole-year statement** (the backend cancel has no kind guard); Replace always errors after the user typed a reason.
- **If left:** after the first year-end run this affects most donors' gifts; one misclick destroys a year-end document only a full batch rerun can regenerate.
- **If fixed:** one filter predicate (use the existing `OFFICIAL_RECEIPT_KINDS` constant, as the backend already does) plus a read-only row for covering statements. Small; keep the statement visible so it isn't hidden entirely.
- **Recommendation: fix.**

### T1-8. Pressing Escape on any confirmation dialog hangs the code awaiting it — worst case leaves the sign-out button permanently dead

- **Where:** the shared dialog host has no `(cancel)`/`(close)` handlers and always renders a native close-on-submit backdrop (confirm-dialog-host.html:1,38 — verified), so Escape (any dialog) or backdrop-click (on "non-dismissible" dialogs) closes the dialog without resolving the promise. The sign-out-failure dialog is non-dismissible by design; dismissing it anyway leaves `signOutInFlight` set forever and every later Sign-out click inert until reload — on the shared-computer scenario the dialog exists for. Also affects the unsaved-changes router guard (sidebar clicks silently do nothing) and both companion apps' end-shift dialogs.
- **If left:** an app-wide class of "the button stopped working" hangs with no error, on every confirm/prompt/choose dialog in three apps.
- **If fixed:** low — the sibling `ModalShell` component already implements the correct pattern in this repo; mirror it (two small handlers, one `@if` around the backdrop). Guard the known double-resolution path (already a no-op via optional chaining) and add Escape/backdrop specs.
- **Recommendation: fix.**

### T1-9. A workspace that cancels its subscription can never reach the Free plan again

- **Where:** both paths that land a tenant on Free after cancellation keep the dead `stripe_subscription_id` (billing/controller.ts:805-815 — verified; :607-617), and the frontend enables the Free card only when that id is empty (`canChooseFree`, billing-settings.ts:119 — verified). The disabled card's message points at a "Downgrade to Free" button that is only rendered for live subscriptions. The backend would accept the call; a test asserts it.
- **If left:** every cancelling workspace dead-ends; `tenant_plan_selected` also stays false, which disables the sending-domain settings section.
- **If fixed:** small, three sites — null the id in both landings, fix the `canChooseFree` predicate. Clearing the id correctly disables "resume" after deletion (nothing to resume) and makes a later reconcile a no-op on an already-Free row.
- **Recommendation: fix.**

### T1-10. A tenant whose renewal payment failed has no working way to switch, downgrade, or cancel

- **Where:** checkout refuses `past_due` with a message naming a "Switch" button (billing/controller.ts:370-377); the frontend treats `past_due` as "no live subscription", so the plan cards call checkout and the cancel button is hidden; the Free card is blocked by T1-9. Only the Stripe portal remains, whose live configuration is a known launch to-do.
- **If left:** the tenants most likely to want a cheaper plan or an exit — the ones whose card just failed — can do nothing, while their sending is already payment-held.
- **If fixed:** low — one shared "subscription exists and is modifiable" predicate (`active`/`trialing`/`past_due`) returned from `getBillingDetails` and used by three frontend computeds. The in-app cancel already accepts `past_due`.
- **Recommendation: fix.**

### T1-11. If production is missing the Stripe webhook signing secret, every billing webhook is silently discarded with a success response

- **Where:** the handler returns early when `STRIPE_WEBHOOK_SECRET` is unset (billing/controller.ts:652-655) and the route replies 200, so Stripe never retries. The production boot-time secret check (`assertProductionSecrets`, env.ts:236-252) verifies four other webhook secrets but not this one; the example env ships `whsec_CHANGE_ME`.
- **If left _and_ the secret is unset in prod:** cancellations never downgrade, payment receipts never send, bracket downgrades never run — billing state frozen, silently. If the secret _is_ set, this is only a missing guard against exactly the config-mistake class that boot check exists for.
- **If fixed:** three lines (add to the boot check; reply 500 when missing so Stripe retries). It will refuse to boot a production environment currently missing the secret — which is the point, but confirm the value is present before deploying the check.
- **Recommendation: fix; operator must confirm the prod value first (open question 2 below).**

## Tier 3 — leave, or fix only when convenient
